# DSH-Memory 全自动长期记忆升级方案

2026-11-06 · 供评审。项目为 `@missher/dsh-memory`，基线为 `0.2.22-native.20261105-recovery2`。下文的新能力、预算和验收目标均为提案。

## 1. 用户应该得到什么

**记得住**意味着今天说过的事实、适用条件和决定理由，过几个会话仍有来源可查。**记得多**意味着原文和历史可以增长，模型每轮只读回答当前问题需要的片段。**记得精**意味着同时问三件事时能找齐三份依据，知道哪个版本还有效，缺哪项就说缺哪项。

用户已经选定日常操作全自动。采集、分段、提炼、选择证据、深查、预算恢复和同步由插件调度。模型工作沿用提问或采集所属会话的宿主路由。用户保有纠正、遗忘、控制花费的入口。沟通偏好可以作为有来源的偏好事实保存，设计范围集中在记忆。

用一个场景贯穿验收。会话 A 确定项目原用 Node 22。会话 B 决定改成 Node 24，并说出升级原因。会话 C 问“现在用什么、以前用什么、当时为什么改”。回答要分别找到现值、旧值和原因。切换到另一个同名项目，三个答案都要重新判断范围。如果当时没有说原因，就只答前两项，明确“没有找到当时说明原因的记录”。

## 2. 哪些证据决定了优先级

现版在真实 DSH 中保存过一条 17,407 字符的明确记忆请求，两个分段覆盖全文，首、中、尾三项事实都被提炼。另一会话实际注入三项并答对。遗忘后第三个会话回答“不记得”，Obsidian 同步也没有将其导回。此前容量版在隔离的 50,000 条记录上逐条读回一致，两次从缓存打开到可检索约 245 和 250 ms，首次构建约 2.19 秒。现有 JSONL、可重建索引、来源日志、任务账本和同步继续作为基础。[安装与容量验收，§67、§70](../../verification.md)

在规划时用已有公开样例，本地拆开了同一套检索结果。每个数表示命中多少个原标注项，沿用评测脚本的查询、候选上限和预算。

| 样例 | 全部标注项 | 初搜 | 内容匹配后 | 自动相关性筛选后 | 排序前五条 | 装进评测文本的记录 ID |
|---|---:|---:|---:|---:|---:|---:|
| 固定 30 题 | 50 | 46 | 39 | 32 | 32 | 32 |
| 独立难例 11 题 | 12 | 12 | 12 | 11 | 11 | 11 |

这里有两种不同的问题。一道题问“注入预算是多少”，旧标注同时要求找回“每天允许几次提炼”。后一项对回答并非必需。另一道题同时问 pnpm 和 Node 版本，两个明确所需的事实都在初搜结果中，相关性筛选却丢了 Node 那条。前者要改评测口径，后者要改产品。旧指标保留，便于前后对照。[固定题、难例和评分逻辑](../../../scripts/eval-recall.mjs)

64% 是旧评测命中的标注项占比（32/50）。它按排序结果计分。生产路径还会使用当前项目、动态预算和用户偏好。现在某条记忆装不下时，后面的短条也会停止尝试。来源引用已能指向消息，但当前摘录取自分段开头，未必是支持该事实的原句。这两点属于代码可见的风险，影响大小要在生产路径上单独测。[提问与注入入口](../../../index.js) · [上下文组装](../../../host/recall.js) · [证据选择](../../../host/capture.js)

## 3. 路线取舍

| 路线 | 能解决什么 | 代价和适用条件 |
|---|---|---|
| 只增强本地检索 | 按子问题找齐证据，保留低延迟和可复查性 | 对说法差异很大、需要理解多段材料的提问，仍可能漏项 |
| **本地优先，按需自动深查** | 简单问题直接回答，复杂问题自动分解、补查合法原文，仍有缺口时让当前宿主模型选证据 | 要处理额外调用的预算、等待时间和未知回执。这是建议主线 |
| 增加本地语义索引 | 改善不同说法之间的候选发现 | 增加模型或运行依赖、磁盘和重建成本。只在剩余失败确实集中于初搜漏召回时做离线对照，再决定是否采用 |

保留当前存储和安装方式，先修已经定位的漏项。知识图谱和 Obsidian 用于浏览、关联和同步。回答所用的证据由受项目范围、有效时间和来源约束的检索路径选择。

## 4. 记忆怎样写得准

1. **原文先落盘，提炼按范围完成。** 复用完整来源、连续分段和持久化任务。短对话与普通长对话也属于验收范围，单独衡量“请记住”和没有提示语的自然聊天。把“请求已完成”“有价值的事实已保存”“无可保存事实”分别统计。
2. **把事实和依据绑紧。** 一个决定可能包含现值、原值、原因、条件。仅保存用户原话实际支持的部分。复用 `sourceRefs`，给能确认的原句附加来源 ID 和可验证的半开字符范围。用原文切片验证数值、单位、否定词及适用对象。多条原话共同支持时分别保留出处。匹配不唯一就保留消息级来源和不确定性。旧记录允许缺少精确定位。
3. **区分谁说的。** 用户确认、助手建议、引用材料、工具输出和内部注入分别处理。助手建议不能自行升级成用户决定。复述、模型输出、同步副本不算独立的用户确认。候选可被后续独立证据自动确认，证据不足时留在候选区，用户无需逐条审批才能继续聊天。
4. **更新要能回答“当时”和“现在”。** 复用 revision、`supersedesId`、`validFrom`、`validTo` 与来源时间。先核对项目、对象和属性，再判断是否真是改值。同一项目两个服务各自用不同版本要并存；同一服务明确从 22 改到 24 才替换。没有明确时间或原因时保留未知。
5. **自动处理能确定的故障。** 原请求未发出的可安全调度，已付费且有返回的优先本地重放，已确认空输出且有改进条件的只补缺失段一次。相同意图复用同一子任务。若宿主能查询回执就自动对账，不能确认是否执行的请求保留未知并继续服务其他工作。沿用每日配额，耗尽后等下一周期自动续跑。

## 5. 一次提问怎样找齐答案

| 步骤 | 默认行为 |
|---|---|
| 确认问题与范围 | 从原始宿主消息找真正的用户提问，忽略插件注入、运行时提示和工具输出。短续问结合前一条真实提问。按当前 profile、项目及允许的全局记忆划定范围，身份不明时收窄查询。换会话或宿主压缩历史后，同一问题仍从持久记忆取证。 |
| 判断用户要几项 | 普通单事实沿用快查。出现“分别”“为什么改”“以前和现在”等结构时，按对象、属性和时间拆成少量子问题。初版建议包括原问题在内最多 4 次本地索引查询。超出时按同一对象合并查找，同时保留未答项。 |
| 为每项找证据 | 对每个子问题分别检索和判断相关性，合并去重。优先为每项各选一条有根据的证据，再考虑同义补充。对灰区候选用具体子问题重新判断。现值优先有效记录；历史值带清楚的时间或已失效标记。 |
| 按预算装入 | 在当前配置预算内优先装回答问题需要的原句或摘要。问沟通偏好时偏好优先；问技术版本时优先技术事实。某条放不下时尝试可验证短摘录或后续短条，保留否定、单位和限定条件。检查最终发给模型的文本确实含有所需值。 |
| 自动深查 | 遇到必答项缺失、版本冲突、或摘要不足且还有可读来源时，先在本地取少量相关原文。存在多个可能解释，才调用当前会话的宿主模型一次，在预先过滤的材料中选来源和引文。模型返回的 ID、摘录、范围由插件本地复核，失败就使用已核实的部分。 |
| 回答与后续 | 给主对话模型提供已证事实、适用范围和具体缺口。没有依据的项允许明确说不知道。深查结果只服务本次回答，新的持久记忆仍须经过正常采集与证据检查。 |

**原文访问同样要遵守遗忘和范围。** 首版只从允许召回的记忆追溯其直接证据。全局偏好可跨项目，但不能借它的引用带出另一项目整段原文。对于“原文有、摘要没收录”的事实，可分批为当前项目内明确允许记忆的用户原文建立可重建的分段索引，每段都要能证明可检索资格。禁止保存、已遗忘、来源不明或归属不清的片段一律排除。读取前和最终注入前均核对当前版本与删除状态。无法证明资格的旧来源只走已有有效引用。没有合格候选就结束查询，不能为了填答案遍历整个 Obsidian 仓库。

**全自动要有调用边界。** 建议首版每个真实用户回合最多 1 次额外深查模型调用，多次 pre-step、工具循环和重启复用同一请求身份；检索本身不触发新的对话采集。普通命中额外调用为 0，无合格材料时也为 0。建议日深查上限从自动总额度的 10% 起步且最多 5 次，计入该总额度；具体数值是设计建议。配额不足、路由不支持、超时或请求结果未知时，用本地可核实的证据继续回答。有界等待，用户取消即停止等待，迟到结果不另发对话。保存 provider 实际回执与用量；项目、记忆版本或权限变化会使旧结果失效。

## 6. 存量、容量和用户控制

- 以权威 JSONL 和已有来源日志为基础。新定位字段可选，老记录仍能搜索。按需补可证明的定位；新增的派生索引在后台分批建立，有游标，可恢复。升级不批量付费重提炼旧库，第一问也不能承担整库扫描。
- 摘要、原文、派生缓存、图谱、后台任务和 Obsidian 回流复用同一套范围和遗忘判定。用户在深查期间遗忘某项，待返回的旧证据也要作废。保留正常软删除和同步恢复副本语义，向用户区分“退出召回”和“物理删除”。
- 自动同步继续使用已有基线。单侧改动自动传播，双侧冲突保留双方，其他记忆继续同步。验证新增字段经过 Markdown 往返能保留，普通笔记或引用不能把项目事实升为全局。
- 日常无需管理任务列表。诊断复用原生 Memory 页面，只在用户查看详情时展示“来自哪次沟通、当前还是历史、这次为什么没用上、是否花了额外调用”。只保留排错需要的标识和计数。后续如改面板，沿用 Corids 的 Apple Design 轻玻璃规范。

## 7. 施工顺序与每批交付物

| 批次 | 先做什么 | 达到什么条件才往下走 |
|---|---|---|
| P0 评测口径与基线 | 在 `scripts/eval-recall.mjs` 保留旧指标，独立标出“必需、可替代、仅相关、禁止”。沿真实 pre-step 路径记录初搜、筛选、排序、最终文本、回答各阶段。建立不参与调参的小型留出集。 | 能解释每个漏项在哪一步消失，区分写入遗漏与召回遗漏。至少复现 pnpm/Node 的明确反例。 |
| P1 本地多线索召回 | 改 `index.js` 的用户提问选择和 `host/recall.js` 的查询、选择与装入。复用 `host/search.js` 的范围过滤、词索引和历史状态。 | 复合提问能同时带回 pnpm 和 Node，现值/旧值标注正确。短续问不被内部消息带偏，单事实和无答案题不退步。 |
| P2 提炼与原句证据 | 在 `host/capture.js`、`host/extract.js`、`host/records.js` 复用分段、引用、版本和替换机制，补精确原句、原因、否定和修正。 | 普通对话与明确记住两条路径分别实测。首中尾原句可核对，同名不同对象不互相替换，旧库继续可读。 |
| P3 自动深查与恢复 | 接入有范围的原文查找、当前宿主模型、回合级去重和预算。复用 `host/capture-journal.js` 的结果已知/未知原则及现有用量记录。 | 能说明深查额外找回了哪项事实。在并发、重启、取消、遗忘时都不重复发同一笔调用；宿主故障或额度用尽仍能完成当前回答。 |
| P4 安装验收与性能 | 同数据比较基线与候选，变更检索或索引后，用已有容量工具对照 5 万条数据。会话和后台捕获空闲时通过宿主插件管理器安装，核版本、运行态、旧库和设置。 | 在隔离 QA 项目和真实宿主模型中完成自然记录、跨会话组合问答、纠正后的今昔查询、遗忘与跨项目负例。只清理 QA 数据。 |
| 条件项 | 只有 P1–P3 后仍有一批明确的同义改写问题在初搜阶段失败，才试本地语义候选。只有证实索引更新或内存阻塞才调整持久化结构。 | 同一批未参与调参的问题上有额外收益，且能承担启动、延迟、存储和维护成本，否则保留已验证策略。 |

## 8. 怎样判定升级确实更好

下列数字是首轮建议验收线，先测基线，再用相同模型、数据、配置和机器比较。旧 30 题和 11 道难例保留为已知回归。新的留出题以事实为单位定答案，允许可替代的表述，一次标注后独立评分。建议从 40 题起步，32 题有答案（至少 16 道需要多条线索），8 道覆盖无依据、遗忘或跨项目。逐题报告分子和分母。

| 能力 | 怎样验收 |
|---|---|
| 采集与提炼 | 允许采集的测试原文逐字一致，分段完整覆盖。明确记住的验收事实全部找到。普通对话按事先标注的应存事实统计提炼覆盖，另计误存。只有摘要、没有可信来源的内容不得计为已证实。 |
| 找全与找准 | 在新留出集的实际注入文本中，必要事实覆盖目标 ≥90%，多线索题所有必答项都齐的题目占比目标 ≥85%。夹带无关事实的题数不高于同集基线。真实回答单独逐项评分，记录答对、漏答、答错、正确指出证据不足。 |
| 范围、时间与遗忘 | 在约定负例中，其他项目专属值、禁止保存值、已忘值的注入数均为 0。事实改值后，问“现在”只用现值，问“当时”保留历史限定，缺失原因不编造。 |
| 容量与响应 | 5 万条隔离数据的全部正文、状态与分页可核对。同机缓存重开至可检索继续以 300 ms 为目标，报告所有样本、首次重建和第一次查询的耗时。普通问题检索 p95 与同机基线对照，建议退化不超过 10%。深查耗时另报。 |
| 花费与故障 | 普通准确命中额外模型调用为 0，深查每回合不超过 1 次，同一已成功或未知请求自动重发数为 0。记录真实用量、配额命中和等待时间。分别验收输出截断、未知回执和预算耗尽。 |

每批独立可用。若某一批增加错误注入、让被遗忘内容复活，或收益只能靠显著放宽预算取得，就停在上一个已验证策略，从失败案例定位。先完成 P0 和 P1，就能知道下一笔工程投入应花在提炼、原文还是语义候选上。
