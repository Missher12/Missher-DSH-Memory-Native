# DSH-Memory 与 Mem0 / OpenViking：下一阶段升级判断

2026-11-07。研究基线为 `@missher/dsh-memory@1.2.0-native.20261107.0` 的实际源码。用户要求继续思考本地记忆系统的优化空间；本轮完成比较、隔离诊断和建议，不修改运行代码、不更换已安装版本、不调用付费模型，也未部署竞品。文中优先级和验收数字是建议目标，不是已经达到的结果。

## 结论

继续沿用当前本地权威记录、来源和遗忘规则，补强检索与证据组织。收益最大的方向是：**多问不漏、换个说法仍能找到、提炼未覆盖的原话也有受控检索路径、跨记录关系能查完整**。数据保存与恢复已有本地验收依据，不能由此推导任意问题的召回质量。

不存在所有指标都无代价提升的“绝对优化”：语义模型、重排、多步查证会增加内存、延迟或调用成本。每一项必须对照同一组问题、相同授权范围和资源预算判断。没有运行同条件竞品对测，因此不宣称优于 Mem0 或 OpenViking。

## 竞品真正值得借鉴的部分

| 维度 | DSH-Memory 当前实现 | Mem0 | OpenViking |
|---|---|---|---|
| 定位 | DSH 原生、本地文件权威、自动捕获与注入 | 可嵌入的记忆库及托管服务；必须区分 OSS 与 Platform | 统一管理记忆、资源和技能的上下文数据库 |
| 检索 | BM25、对象/属性/时间规则、授权引文、有限候选模型选择 | 向量检索、实体信号及可选重排；Platform 另有图关系、时间等能力 | 向量检索、可选意图拆解和重排，可按范围与内容层筛选 |
| 原始证据 | 保存完整允许采集的原文；当前原文索引依赖已提炼记录的短引文 | 默认保存提炼事实；需要原样内容时另用直接存储方式 | 会话归档及资源正文，配合目录摘要与概览 |
| 演变 | 修订、替代关系、有效时间、删除标记；基于规则的合并和维护 | Platform Dream 提供合并、旧事实替代及可选模式归纳 | 会话提交后台提炼，更新写入 memory diff，可配置记忆类型 |
| 本地使用成本 | 无外部数据库依赖，已集成当前宿主模型、原生页面及 Obsidian | OSS 需配置模型、向量存储和可选重排；托管版由服务方运行 | 引入独立上下文服务、索引及模型配置的范围更大 |

Mem0 的当前官方说明将 OSS 的实体加权和 Platform 的 Graph Memory 分开；时间推理、Dream 等也不能当成开源库已经提供。当前 OSS 源码仍实际调用 embedder/vector store，并支持可选 reranker。[Mem0 工作机制](https://docs.mem0.ai/core-concepts/how-it-works)、[Platform 与 OSS 对照](https://docs.mem0.ai/platform/platform-vs-oss)、[OSS 源码](https://github.com/mem0ai/mem0/blob/main/mem0/memory/main.py)

OpenViking 的 L0 是目录摘要、L1 是目录概览、L2 是正文，不能与旧 TDAI 的层名直接对应。其当前检索文档及 `HierarchicalRetriever` 源码实际执行每查询一次全局向量检索和可选重排；不能按旧宣传把它描述成每次逐层递归遍历目录。分层内容仍可供按需阅读。[内容分层](https://docs.openviking.ai/en/concepts/03-context-layers)、[检索机制](https://docs.openviking.ai/en/concepts/07-retrieval)、[检索源码](https://github.com/volcengine/OpenViking/blob/main/openviking/retrieve/hierarchical_retriever.py)

后台整理值得参考，但“归纳出的模式”应与原话事实分开。我们保留用户已确定的范围：不恢复人格/灵魂，不接管 MSE 的经验学习或 Context 的上下文压缩。[Mem0 Dream](https://docs.mem0.ai/platform/features/dream)、[OpenViking 会话管理](https://docs.openviking.ai/en/concepts/08-session)

## 当前源码中确定的缺口

1. **复合问题仍有硬限制。** `host/recall.js` 的 `recallQueryPlan()` 限制 `plan.length < 4`，主问题也占一项。`host/recall-selection.js` 另限制最多 4 个补查槽位。复杂枚举可能被合并，不能用已有两项或三项成功来证明五项也完整。
2. **候选入口主要仍是词法。** `host/search.js` 是 BM25；`index.js` 的 `recallCandidatePool()` 使用词法命中和每作用域最多 80 条兜底，再缩成 24 条，发送时还受输入预算限制。选择模型看不到的事实无法靠更强的选择模型找回来。当前没有真正接入向量语义检索。
3. **完整保存不等于完整可检索。** `host/source-index.js` 只把当前项目 active 记录所绑定、具有合法来源字段且不超过 240 字符的用户引文加入候选索引。未被提炼记录引用的原文，不具备同等候选入口。现有授权限制不能为了召回率直接取消。
4. **图谱展示尚未成为关系推理。** 当前召回没有把“服务 → 审批人 → 替补”作为可追踪的多步证据链检索。找到相关实体不等于回答了问题要求的关系。
5. **覆盖状态在最终裁剪之前计算。** `index.js` 的 `updateLastRecall()` 在 `compileMemoryContext()` 之前更新；后者仍可能因条数和 token 预算减少实际注入。报告“找到的证据”和“真正送给回答模型的证据”需要分开。该项为源码确认的结构性风险，本轮未单独制造 token 截断用例。
6. **大库指标覆盖范围有限。** 50k 验收主要覆盖记忆记录；知识索引启动时扫描笔记，原文候选查询仍遍历当前项目记录。5 万条短记忆不代表 5 万篇长笔记、数百万原文段或长期写入下有相同性能。现有 40 题也是较小的固定工程事实集，不能外推为通用准确率。

## 本轮隔离诊断

使用生产 `agent/pre-step`，在临时目录中准备 8 条目标事实及 120 条无关记录。补查模型由只记录候选并返回空选择的模拟适配器代替；因此结果衡量本地检索/规划及候选可达性，不是实际模型答题分数。没有读取或改写真实记忆。

| 检查 | 观察 | 能得出的结论 |
|---|---|---|
| 同时问 pnpm 和 Node | 两项均注入 | 原有两项路径仍有效 |
| 同时问 pnpm、Node、Redis、PostgreSQL、Vite | 本地注入 2/5；后三项合成一个补查槽位，候选中有全部事实 | 问题拆分存在具体缺口；空选择器下的 2/5 不是实际模型最终分数 |
| 不出现 Node 名称，以英语询问后端 JavaScript runtime | 正确 Node 记录未进入发送的补查候选 | 当前候选入口无法支持这个跨语言改写；更换选择模型本身不能补救 |
| 问陈蔚的替补 | 注入林汀 | 第二段关系本身可检索 |
| 问蓝湾服务审批人请假后谁接手 | 只注入审批人为陈蔚；没有继续补查替补 | 关系链不完整，不能把局部相关记忆视为完整答案 |

中文同义改写的补查候选实际包含正确记录，不能仅因空选择器没有返回答案就判定真实模型失败。最初改写含“当时”，同时触发历史意图；另用去掉该词的问句隔离此因素，只重跑这一例。英语含 Node 名称的查询也有正确候选，和不含名称的语义问题分开记录。

复跑脚本及原始结果位于 Git 忽略目录 `docs/tasks/competitive-research-20261107/`。这组诊断专门找边界，样本少且由本次审查者构造，不能作为竞品排名或泛化准确率。

## 建议实施顺序

### P0：多问覆盖与最终注入一致

- 将枚举中的对象与属性分别保留，覆盖跟踪不再因固定四项而丢掉用户问题；每个待答项分配候选，避免前三项挤占全部预算。
- 最终按实际注入内容计算覆盖。分别显示已检索、已注入及仍缺依据；预算不足时明确剩余项，不把相关的一句话计作完整回答。
- 复杂问题采用有总时间/token 上限的自动分批查证。普通短问题沿用快速路径；不无限扩大单次 prompt，也不自动提高用户付费预算。
- 验收：新增 5–8 对象、不同属性、重复别名、token 不足、当前/旧值混问；足够预算时所有有依据项进入注入，预算不足时缺项报告准确。既有 40 题、隔离和遗忘检查不得退化。

### P1：混合语义检索与受控原文分段索引

- 保留关键词检索对版本号、路径和编号的精确性，增加多语种语义候选；融合后再按对象、时间、范围和原文核验。先确保正确证据进入候选，再考虑小规模重排。
- 向量只是可重建派生索引。记录版本、模型版本和删除状态对应，失效时回退词法；语义相似不能直接判定事实成立，也不能覆盖精确数值与否定条件。
- 原文建立可重建分段索引，记录来源、范围、说话角色和授权状态。仅有保存文件不足以授权跨会话注入；新增明确的来源检索授权，并保留不保存、引用、敏感内容、项目边界和遗忘屏障。老来源没有足够授权时继续拒绝。
- 未提炼的有效原话可作为“原始证据”被查回，不自动升级为已确认事实。需要区分问题、假设、引用与决定，避免把用户提问当成用户事实。
- 默认建议本地多语种小模型、懒加载和后台增量处理；先核对真实宿主是否暴露 embedding 能力。聊天模型接口不能冒充 embedding 接口；若需本地运行时，要验证 DSH 签名/加载约束、内存和中文效果，再选具体模型。本轮未安装依赖或预选付费服务。
- 验收：专门的中文改写/中英混问、原文中未提炼细节集，候选覆盖明显高于当前基线，精确值与否定条件不退化。检索前和注入前均执行范围/遗忘检查，向量过期或不可用仍能正常运行。

### P2：实体、关系与时间线

- 先支持有原句依据的少数关系：别名、负责人/替补、决定/原因、旧值/新值；按当前问题最多追加有限关系追查。无需一开始引入独立图数据库。
- 每一步携带来源、有效时间和作用域；别名不能靠同名猜，跨实体不能靠向量相似拼接。某条边缺证据时报告缺口。
- 项目摘要和主题概览作为导航，链接回原文和有效记录，按来源变化失效。不能用自动摘要替换权威正文，也不能因总结而使已遗忘内容复活。
- 验收：审批人→替补的两跳样例、同名不同项目、生产/测试不同配置、先宣布后生效、迟到历史消息及决定原因；每个回答值能回指有效原句。

### P3：真实混合容量与队列体验

- 以“记忆记录 + 长原文分段 + 知识笔记”混合数据测量，分别报告首次构建、缓存重开、查询 p95、事件循环延迟、内存、磁盘和增量更新成本。
- 源索引改为按变更增量更新，知识/语义构建移出宿主同步热路径；后台进度必须准确，不能跳过未建索引内容后报告全库已就绪。
- 预算等待显示原因和下次可处理时间；优先处理显式记忆和影响当前问答的尚未发送任务。已完成回执复用，结果未知仍不重发；原文兜底改善等待期间可查性，不能通过偷偷提高预算解决积压。
- 目标：指定机器与公开语料上，50k 缓存重开 p95 争取 ≤300ms；首次构建与知识/原文索引另计，不包装成全宿主冷启动。新增语义路径单列模型加载、首查和稳定态耗时，只有质量收益成立才接受额外成本。

## 如何判断升级是否真的更好

先扩展到至少 200 个有原句答案的隔离问题，覆盖直接问、改写、跨语言、多项、多跳、时序、否定/条件、未提炼细节、遗忘和越权。开发用例与最终保留集分开，不能针对保留题改规则后仍称独立盲测。记录候选覆盖、最终注入覆盖、无依据内容、端到端回答、延迟和实际模型用量。

建议质量目标：复杂改写集相对当前基线至少提高 15 个百分点；精确值与现有已验证场景不退化；限定负例集越权、遗忘复活及未知请求重发均为 0。零错误只是该组验证结果，不能外推成无条件保证。真实宿主只需选择能区分方案的少量新会话问题，按实际回执计费。

需要与竞品比较时，先固定同一批隔离对话、相同回答模型、上下文预算和问题；分别报告 Mem0 OSS、Mem0 Platform、OpenViking 的版本、配置和成本。提炼与嵌入成本必须计入，不能拿我们 40 道固定题的注入成绩对比别人的 LoCoMo 模型回答分数。[Mem0 评测说明](https://docs.mem0.ai/core-concepts/memory-evaluation)

## 路线选择

- **推荐：在当前本地实现上分阶段增强。** 先做可直接复现的 P0，再做 P1，随后按困难问题证据推进 P2/P3；保留现有完整来源、删除屏障、原生管理和同步。
- **备选：替换为 Mem0 OSS 后端。** 可复用语义基础设施，但已有来源权限、遗忘、回执、恢复与 DSH 生命周期仍需适配；不能假设换库自动解决多问覆盖。
- **备选：采用完整 OpenViking 服务。** 适合未来明确需要跨应用统一资源/技能平台时再评估，当前会显著扩大部署与迁移范围。

本轮研究目标完成。运行中的插件保持 1.2.0，以上升级尚未实施；下一项最明确的开发工作是 P0 的多项拆分与最终注入覆盖修复。
